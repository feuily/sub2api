# Wire 是怎么把服务拼起来的

这篇文档只回答几个实际问题：

- `wire.go` 和 `wire_gen.go` 分别是什么？
- 新功能什么时候要重新生成 Wire？
- 服务启动时，配置、数据库、业务服务和 HTTP Server 是怎么连起来的？

## 先记住这三句话

1. **`wire.go` 是人写的装配说明。**
2. **`wire_gen.go` 是 Wire 根据说明生成的 Go 代码。**
3. **服务启动时只运行生成好的代码，不会现场运行 Wire 生成代码。**

入口在 [`main.go:151`](../../backend/cmd/server/main.go#L151)，装配说明在 [`wire.go:34`](../../backend/cmd/server/wire.go#L34)，生成代码在 [`wire_gen.go:32`](../../backend/cmd/server/wire_gen.go#L32)。

## 用“插头和插座”理解 Wire

假设一个服务需要数据库：

```go
func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo: repo}
}
```

这个函数相当于说：“创建 `UserService` 时，我需要一个 `UserRepository`。”

另一个构造函数负责提供这个 repository：

```go
func NewUserRepository(db *sql.DB) UserRepository {
    return &userRepository{db: db}
}
```

它又表示：“创建 `UserRepository` 时，我需要一个数据库连接。”

Wire 会根据函数参数和返回值的类型，把这些插头和插座接起来：

```text
*sql.DB -> UserRepository -> UserService
```

简单说：**函数参数写需要什么，返回值写能提供什么；Wire 按类型把它们连起来。**

Wire 在生成代码时会检查依赖能不能接上。比如缺少某种类型的 provider，或者有两个 provider 都提供同一种类型，生成时就会报错。

## 两个文件分别怎么用

| 文件 | 谁维护 | 用途 |
|---|---|---|
| [`wire.go:1`](../../backend/cmd/server/wire.go#L1) | 开发者手写 | 写 `Application`、告诉 Wire 可以使用哪些 provider，以及项目自己的辅助 provider。 |
| [`wire_gen.go:1`](../../backend/cmd/server/wire_gen.go#L1) | Wire 生成 | 写实际的创建顺序和函数调用。不要手动修改。 |

`wire.go` 开头的 `wireinject` 表示它是给 Wire 生成器用的。里面的 `initializeApplication` 会写 `wire.Build(...)`，后面的 `return nil, nil` 只是占位，不是服务启动时执行的代码（[`wire.go:1`](../../backend/cmd/server/wire.go#L1)、[`wire.go:34`](../../backend/cmd/server/wire.go#L34)）。

普通编译使用的是 `wire_gen.go` 里的 `initializeApplication`。生成文件有 `!wireinject` 标记，文件头也写着 `Code generated by Wire`（[`wire_gen.go:1`](../../backend/cmd/server/wire_gen.go#L1)、[`wire_gen.go:6`](../../backend/cmd/server/wire_gen.go#L6)）。

要注意：`wire.go` 里不只有装配说明，也有开发者手写的真实函数，比如清理后台服务的 `provideCleanup`。这些函数仍然是项目源码，要正常维护（[`wire.go:84`](../../backend/cmd/server/wire.go#L84)）。

## 本项目启动时，依赖怎么接起来

可以把整个过程看成一条流水线：

```text
配置
  ↓
数据库、Redis
  ↓
Repository（读写数据）
  ↓
Service（处理业务）
  ├─ Middleware（认证、审计等）
  └─ Handler（处理 HTTP 请求）
         ↓
      Gin Router
         ↓
      HTTP Server
```

本项目里对应的代码是：

1. 配置层提供 `*config.Config`（[`config/wire.go:11`](../../backend/internal/config/wire.go#L11)）。
2. Repository 层根据配置建立 Ent、SQL 和 Redis 等依赖（[`repository/wire.go:185`](../../backend/internal/repository/wire.go#L185)、[`repository/wire.go:211`](../../backend/internal/repository/wire.go#L211)、[`repository/wire.go:234`](../../backend/internal/repository/wire.go#L234)）。
3. Service 使用 repository 和配置实现业务。各层的 provider 放在自己的 `ProviderSet` 里，例如 [`repository/wire.go:67`](../../backend/internal/repository/wire.go#L67) 和 [`service/wire.go:859`](../../backend/internal/service/wire.go#L859)。
4. Middleware 和 Handler 使用需要的 service。Handler 最后会被组合成一个 `handler.Handlers`（[`middleware/wire.go:21`](../../backend/internal/server/middleware/wire.go#L21)、[`handler/wire.go:183`](../../backend/internal/handler/wire.go#L183)）。
5. Server 使用配置、handlers 和中间件创建 Gin Router，再把它包装成 Go 的 `http.Server`（[`http.go:30`](../../backend/internal/server/http.go#L30)、[`http.go:113`](../../backend/internal/server/http.go#L113)）。
6. Wire 把最终结果放进 `Application`，返回给 `main.go`（[`wire.go:27`](../../backend/cmd/server/wire.go#L27)、[`wire.go:61`](../../backend/cmd/server/wire.go#L61)）。

主 injector 在 [`wire.go:34`](../../backend/cmd/server/wire.go#L34)。里面的 `wire.Build(...)` 列出了配置、repository、service、middleware、handler 和 server 等 provider set（[`wire.go:35`](../../backend/cmd/server/wire.go#L35) 至 [`wire.go:60`](../../backend/cmd/server/wire.go#L60)）。

不用猜顺序的话，可以直接看生成代码：它先加载配置，再创建数据库和 repository，之后创建 service、handler、中间件、router 和 HTTP Server（[`wire_gen.go:34`](../../backend/cmd/server/wire_gen.go#L34)、[`wire_gen.go:331`](../../backend/cmd/server/wire_gen.go#L331)、[`wire_gen.go:338`](../../backend/cmd/server/wire_gen.go#L338)）。

## 进阶用法：本项目怎么处理复杂情况

前面的例子是“一条线接到底”。实际项目通常还有接口、后台任务、动态配置和很多模块。Wire 也能把这些依赖清楚地接起来。

### 1. 一个对象可以通过多个接口使用

有时同一个对象承担多个职责。例如安全审计模块的 `PostgreSQLRepository` 同时作为任务仓库和事件仓库使用：

```go
NewPostgreSQLRepository,
wire.Bind(new(JobRepository), new(*PostgreSQLRepository)),
wire.Bind(new(EventRepository), new(*PostgreSQLRepository)),
```

这表示：创建一个 `PostgreSQLRepository`，需要 `JobRepository` 时把它当任务仓库用，需要 `EventRepository` 时把同一个实现当事件仓库用。`wire.Bind` **只声明接口对应哪个实现，不负责创建对象**。实际绑定见 [`prompt_module.go:5`](../../backend/internal/securityaudit/prompt_module.go#L5) 至 [`prompt_module.go:8`](../../backend/internal/securityaudit/prompt_module.go#L8)。

这适合“实现稳定、调用方只需要接口”的情况，也方便测试时换成 mock 实现。接口不必为了 Wire 而到处新增；只在确实需要隔离实现时使用。

### 2. 用 Provider 包装已有构造函数

有些对象不能只靠一个 `NewXxx(...)` 完成初始化，还需要设置可选依赖或兼容旧构造方式。本项目通过 Provider 包装它：

```go
func ProvideAuthService(/* required dependencies */) *AuthService {
    svc := NewAuthService(/* existing constructor arguments */)
    svc.SetTencentCaptchaService(tencentCaptchaService)
    svc.SetAliyunCaptchaService(aliyunCaptchaService)
    return svc
}
```

Wire 调用 `ProvideAuthService`，而不是直接调用 `NewAuthService`；Provider 负责先创建，再补齐验证码依赖。这样可以保留原构造函数的用法，同时让正式应用拿到配置完整的服务。项目实现见 [`service/wire.go:58`](../../backend/internal/service/wire.go#L58) 至 [`service/wire.go:92`](../../backend/internal/service/wire.go#L92)。

**什么时候用：**需要适配旧构造函数、初始化后还要设置依赖，或构造时要做少量明确的组装工作。不要把复杂业务逻辑塞进 Provider。

### 3. 注入工厂，而不是固定的对象

有些资源的配置会在程序运行期间变化。启动时就创建一个固定客户端，配置更新后可能无法使用新配置。此时可以注入“工厂函数”，在真正需要资源时再根据当时的配置创建对象。

本项目的图片存储就是这种情况：Wire 提供 `ImageStorageFactory`，调用工厂时再传入当时的图片存储配置，创建对象存储客户端（[`repository/wire.go:190`](../../backend/internal/repository/wire.go#L190) 至 [`repository/wire.go:196`](../../backend/internal/repository/wire.go#L196)）。

```text
Wire 注入 ImageStorageFactory
          ↓
业务拿到最新配置后调用工厂
          ↓
创建匹配当前配置的 Storage
```

**什么时候用：**依赖需要按请求、任务或最新设置创建；不要为了“灵活”把所有依赖都改成工厂，固定且共享的数据库、Redis 等仍应作为对象注入。

### 4. 只组装应用需要的结构体字段

主 injector 用 `wire.Struct` 创建 `Application`，并明确只填 `Server`、`PromptAudit`、`PluginManager`、`Cleanup` 四个字段（[`wire.go:61`](../../backend/cmd/server/wire.go#L61)）。

```go
wire.Struct(new(Application), "Server", "PromptAudit", "PluginManager", "Cleanup")
```

这样新增 `Application` 字段时，不会不知不觉地把它也加入依赖图；需要暴露给启动入口的字段必须明确列出。这让 `Application` 成为清楚的边界：main 只拿它需要启动和关闭的对象。

### 5. 把后台服务的关闭也接进依赖图

Wire 不会自动调用 `Stop()` 或 `Close()`。本项目用 `provideCleanup` 明确列出需要停止的后台服务，并最后关闭 Redis 和 Ent 连接（[`wire.go:84`](../../backend/cmd/server/wire.go#L84)、[`wire.go:404`](../../backend/cmd/server/wire.go#L404)、[`wire.go:447`](../../backend/cmd/server/wire.go#L447)）。

`Application` 持有生成出来的 Cleanup 函数；`main.go` 在启动时注册 `defer app.Cleanup()`，因此服务退出时会执行这些清理步骤（[`wire.go:61`](../../backend/cmd/server/wire.go#L61)、[`main.go:155`](../../backend/cmd/server/main.go#L155)）。

**实际意义：**增加一个会启动 goroutine、定时器或订阅的服务时，不仅要让 Wire 创建它，也要考虑它怎样停止。否则进程关闭时可能留下未停止的任务，或者在数据库/Redis 已关闭后仍尝试访问它们。

## 新功能什么时候要重新生成

**不是每写完一个功能都要生成 Wire。**看这次改动有没有影响“对象怎么创建、依赖怎么传”：

| 改动内容 | 是否需要生成 |
|---|---|
| 改 handler 里的业务逻辑 | 通常不需要 |
| 改已有 service 的业务逻辑，但构造参数没变 | 通常不需要 |
| 新增路由，使用已经存在的 handler 和依赖 | 通常不需要 |
| 给构造函数增加依赖参数 | 需要 |
| 新增 provider，并希望 Wire 创建它 | 需要 |
| 修改 ProviderSet 或接口绑定 | 需要 |

### 只生成 Wire

在 `backend/` 目录执行：

```bash
go generate ./cmd/server
```

它会读取 [`wire_gen.go:3`](../../backend/cmd/server/wire_gen.go#L3) 声明的命令，运行 Wire 并更新 `wire_gen.go`。Wire 版本由 [`backend/go.mod:26`](../../backend/go.mod#L26) 管理。

### 重新生成所有代码

如果还改了 Ent schema，或者确实需要重新生成 Ent 和 Wire，在 `backend/` 目录执行：

```bash
make generate
```

它会依次生成 Ent 和 Wire（[`Makefile:9`](../../backend/Makefile#L9) 至 [`Makefile:11`](../../backend/Makefile#L11)）。只改 Wire 时，用 `go generate ./cmd/server` 就够了。

生成之后，检查变更并编译：

```bash
go test ./cmd/server
git diff --check
git status --short
```

## 如果不使用 Wire 呢？

服务仍然可以运行。只是现在 Wire 自动生成的创建代码，要改成开发者自己在一个初始化函数里写出来：

```text
先读配置
再创建数据库和 Redis
再创建 repository
再创建 service
再创建 handler 和 middleware
再创建 router 和 HTTP Server
```

这通常叫“手动装配”。Go 编译器仍会检查函数参数类型，但所有创建顺序、依赖传递、错误处理和资源关闭都要手动维护。项目依赖较多时，初始化函数会变得很长，也更容易漏接新依赖。

Wire 的好处是自动检查依赖有没有接上，并生成明确的 Go 代码；坏处是增加了 `wire.go`、生成命令和 `wire_gen.go` 这套维护流程。**它不会改变服务运行方式，也不会在服务启动时帮你生成代码。**

## 最简单的阅读顺序

第一次看启动装配，按这四步读就行：

1. 看 [`main.go:151`](../../backend/cmd/server/main.go#L151)：main 在哪里调用装配函数。
2. 看 [`wire.go:34`](../../backend/cmd/server/wire.go#L34)：告诉 Wire 可以用哪些依赖。
3. 看 [`wire_gen.go:32`](../../backend/cmd/server/wire_gen.go#L32)：实际对象是怎么依次创建的。
4. 看 [`http.go:30`](../../backend/internal/server/http.go#L30) 和 [`http.go:113`](../../backend/internal/server/http.go#L113)：Router 和 HTTP Server 是怎么形成的。

只要记住：**`wire.go` 写规则，命令生成 `wire_gen.go`，服务启动时运行生成好的代码**，就不会被 `main.go` 里看不到大量 `NewXxx()` 调用这件事绕晕。
